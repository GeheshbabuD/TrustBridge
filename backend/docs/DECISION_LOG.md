| ADR-018 | JWT and refresh-session lifecycle | Access JWTs use validated HS256 key, issuer, audience and TTL, current authorization version, and refresh-session ID; only MFA-completed sessions receive signed `mfa_at`. Refresh tokens are 32 random bytes stored only as SHA-256 digests. Atomic conditional rotation maintains one unique successor; replay revokes its token family. Password-only USER JWTs remain valid until expiry after logout; MFA-assured requests check the linked row and fail after revocation. | Accepted in TB-BE-032; assurance additions TB-BE-034D |
| ADR-019 | Authorization and resource lookup policy | Account roles remain `USER`/`ADMIN`; participant roles remain `BUYER`/`SELLER`. | ADR-020 | Privileged MFA and recovery persistence | ADMIN TOTP is mandatory and USER TOTP optional; 6 digits, 30-second period, `MFA_TOTP_WINDOW_STEPS` defaulting to one (bounded 0–2). Generate ten 128-bit single-use recovery codes; persist hashes only. TOTP secrets use AES-256-GCM through a provider-neutral encryption-provider interface that does not export raw keys, with user/purpose-bound AAD and key ID/version. Local 32-byte base64 key is development/test-only; production KMS vendor and lifecycle remain unselected and are a production gate. Admin account recovery requires independent identity verification plus two distinct active ADMIN approvals; no self-approval. No trusted devices. Persistence is 034B; enrollment is 034C; login assurance is 034D; purpose-bound step-up is 034E; recovery completion is 034F. | Approved defaults in TB-BE-034A; staged implementation; production KMS and recovery governance remain gates |
| ADR-021 | TOTP enrollment and verification | Implement RFC 6238 with SHA-1, six digits, 30-second period and validated 0–2 step skew (default one); use Node crypto HMAC and timing-safe comparison, no added dependency. Enrollment returns provisioning secret/URI once, stores only through encrypted 034B interface, and requires code verification. Atomic activation plus first hash-only recovery-code batch; replay guarded by conditional DB update. Failed verify limit defaults to 5 per authenticated user per 10 minutes; current in-memory store requires shared store before horizontal scale. Login challenge is 034D; purpose-bound step-up is 034E. | Accepted in TB-BE-034C; production KMS remains prerequisite |
| ADR-022 | MFA login challenges and session assurance | Active-MFA accounts and ADMINs use a five-minute default, hash-only LOGIN challenge with five persistent code attempts. One serializable transaction validates current account/MFA/authVersion, consumes the challenge and compare-and-set claims the TOTP step. Only then are refresh/access credentials created. JWT assurance uses `mfa_at` plus persisted `sid`; refresh cannot elevate it. Recent assurance defaults to 15 minutes. Login/challenge IP limits are process-local pending shared-store infrastructure. Existing ADMIN accounts without active MFA cannot receive a normal login session; controlled bootstrap/enrollment is deferred to 034G. | Accepted in TB-BE-034D; step-up/security scope in 034E |
| ADR-023 | Purpose-bound MFA step-up assurance | Step-up is represented by the successfully consumed `MfaChallenge` row, not by JWT mutation. Bind user, live refresh-session FK, authVersion, explicit allowlisted operation purpose, resource type/ID, exact MFA `enabledAt`, expiry, attempt count and server-set verifiedAt. Challenge category enum `purpose=STEP_UP` is distinct from `operationPurpose`. TOTP-step claim plus challenge consume run in one serializable transaction. Five-minute challenge/assurance defaults, five persistent failures. Middleware queries the durable grant and independently requires authentication plus role/ownership policy. Registry currently contains only self `MFA_RECOVERY_CODES_REGENERATE`; the operation and all financial/admin business operations are unimplemented.
