# TB-BE-053 — Backend Authorization and Access-Control Security Audit

**Assessment only.** No code, tests, schema, database, provider, or recovery-document changes were made. Review was limited to shared auth/role/ownership middleware, auth/user/transaction/dispute/escrow/admin routes and services, plus focused tests.

## Summary

No confirmed cross-user or cross-transaction IDOR was found in the inspected profile, transaction, invitation, dispute, evidence, notification, or escrow paths. Protected resources are generally authorized from persisted session/user state and persisted resource relationships, with ownership rechecked in services for mutations and sensitive reads. ADMIN does not receive a general ownership bypass. The most concrete hardening gap is that the ADMIN legacy-MFA onboarding inventory and request-creation routes require ADMIN role and rate limiting, but not recent TOTP/step-up; identity verification, approval, and enrollment-authorization issuance do require purpose-bound step-up. Ordinary account-recovery service operations have no corresponding HTTP routes in the inspected auth router, so that workflow is not externally available there; this is a completeness limitation, not an access bypass.

## Findings

### MEDIUM — Legacy ADMIN MFA onboarding inventory/request initiation lacks recent TOTP

- **Impact:** An authenticated ADMIN session can enumerate active ADMIN accounts without enabled MFA (including email addresses) and create a legacy-enrollment recovery request without proving recent TOTP. The later identity-verification, approval, and enrollment-authorization steps are more strongly gated, so this is not evidence that an attacker can complete recovery or obtain an enrollment authorization. It unnecessarily exposes sensitive recovery targets and permits workflow initiation from a stale authenticated session.
- **Affected code:** `src/routes/auth.routes.js`: `GET /mfa/admin-enrollment/legacy-admins` and `POST /mfa/admin-enrollment/requests` use authentication, `requireRole("ADMIN")`, and a rate limiter, but no recent-MFA/step-up middleware. `src/services/mfa.service.js:listLegacyAdminAccounts` returns IDs and emails for active legacy ADMIN accounts. `createLegacyAdminEnrollmentRequest` creates a time-limited request after persistence checks the target is active ADMIN without enabled MFA and prevents duplicate pending requests.
- **Test evidence:** `tests/unit/mfa-service.test.js` covers listing behavior. Focused test search found no HTTP test for these two paths asserting recent-TOTP enforcement. `tests/integration/mfa-recovery-governance.test.js` covers recovery-code regeneration, not legacy-admin inventory/request authorization. Subsequent recovery steps have route-level step-up configuration in `auth.routes.js`, but this does not cover initiation/listing.
- **Minimal correction:** Require fresh server-validated TOTP assurance for both routes (using an approved existing recent-MFA policy; use purpose-bound step-up if the operation is designated one-time/sensitive). Add HTTP tests that stale/password-only/recovery-code assurance is denied, fresh TOTP ADMIN is allowed, and non-ADMIN is denied. Do not weaken the existing identity verification, two-distinct-admin approval, or enrollment-token gates.

### LOW — Ordinary account-recovery service workflow has no HTTP entry points in the inspected router

- **Impact:** `createAccountRecoveryRequest`, identity verification, approval, and completion are exposed by the MFA service object but do not appear as routes in `src/routes/auth.routes.js`. Users cannot invoke the ordinary recovery governance workflow through this API surface. This is a missing integration surface, not a demonstrated unauthorized operation.
- **Affected code:** `src/services/mfa.service.js` exposes the methods; `src/services/mfa-persistence.service.js` implements durable request, identity, approval, and completion controls. No matching account-recovery endpoint was found in the inspected route/controller files. Existing HTTP governance coverage is focused on regeneration and legacy-admin recovery endpoints.
- **Test evidence:** Persistence and service tests cover governance rules; no matching ordinary account-recovery HTTP route test was found in the scoped test search.
- **Minimal correction:** Confirm product intent and the independent identity-verification/delivery provider boundary, then expose only the approved workflow through authenticated/anonymous-safe routes with strict enumeration resistance, rate limits, audit, and end-to-end authorization tests. Do not add a weaker recovery path to compensate for the missing routes.

## Coverage limitations and decisions

- Unit and HTTP mocks establish route/middleware policy but do not prove database locking or isolation; rely on the relevant isolated PostgreSQL suites for those concurrency properties.
- No matching ordinary account-recovery HTTP workflow was found. Whether it should be exposed, and through what identity-verification and secure-delivery providers, requires product/security/provider approval.
- Whether legacy ADMIN inventory/request initiation requires recent TOTP or a purpose-bound, one-time grant should be explicitly confirmed by Security; current adjacent admin operations indicate the intended high-assurance pattern.
- The audit did not inspect database contents, secrets, provider systems, or production configuration.

## Prioritized remediation

1. Add fresh server-side TOTP/step-up protection to legacy ADMIN onboarding inventory and request initiation; add HTTP regression tests (MEDIUM).
2. Decide whether ordinary account recovery should have an HTTP surface; unblock only after identity-verification, secure-delivery, rate-limit, privacy, and authorization policies are approved (LOW / provider-dependent).
3. Keep existing transaction/participant, dispute/evidence, session, and financial ownership checks intact; expand PostgreSQL concurrency coverage only where isolated infrastructure is explicitly available.

No remediation was implemented in this audit.
