# Security Plan

Assets: credentials, tokens, terms, payment references, ledger, evidence, admin actions, AI outputs and secrets. Boundaries: client/API, app/database, provider APIs, chain, admin and upload storage. Implemented HTTP baseline (TB-BE-012/013): Helmet defaults with CSP disabled; exact HTTP(S) CORS allowlist from validated config; generated or syntax-checked request IDs; 1 MiB JSON/form body limits and a 1000 URL-encoded parameter cap; API-only 100-request/15-minute default rate limit; stable JSON 404/error responses that do not echo parser bodies, unknown exception text or stacks. TB-BE-014 logs one JSON completion record containing only request ID, method, route template/unmatched marker, status, duration, timestamp, level and event; it omits query strings and all headers/bodies. `/health` and `/health/live` report process liveness only; `/health/ready` returns 503 and `database: not_checked` until a real database probe exists. Missing CORS allowlist denies browser-origin requests while originless health probes can proceed. Other controls below remain planned for their assigned tasks.

The only approved local development/testing database target is PostgreSQL 17.10 at `localhost:5432/Trustbridge`. Keep the development URL bound to this local endpoint; production credentials or external hosts must not be used for migration work.

TB-BE-025's reviewed initial migration is applied to the approved local-only PostgreSQL 17.10 target (`Trustbridge`, `localhost:5432`) and recorded as successful. Preserve the migration metadata and do not redirect database operations to remote, production, shared or unidentified targets. The migration's 11 custom CHECK constraints were confirmed validated and exercised with rolled-back constraint probes.

## TB-BE-024 persistence safeguards

Refresh sessions persist only a unique token hash, never the bearer token, and retain family/predecessor lineage plus expiry, revocation and reuse-detection timestamps. Token hash algorithm, rotation atomicity, replay response and family revocation remain service-level controls. AI JSON must be minimized/redacted and remains advisory. Blockchain rows retain hashes/references only; PII, evidence, credentials and private keys stay off-chain and out of this schema. Restrictive foreign keys preserve history. Schema declarations do not themselves enforce JSON redaction, immutable histories, subject validity, token lifecycle consistency, or chain finality.

| Threat | Risk | Planned controls |
|---|---|---|
| Credential abuse/token theft | High | bcrypt, generic errors, rate limits, short JWT, hashed rotating refresh tokens |
| Broken object authorization/escalation | Critical | default deny, role+ownership checks in services, adversarial tests, MFA/step-up authentication for admin and sensitive financial actions |
| Forged/replayed webhooks | Critical | server verification, raw-body signature, replay window, idempotency and reconciliation |
| Duplicate payout/race | Critical | unique op key, DB transaction/locking, policy authorization, provider idempotency |
| Injection/mass assignment | High | Prisma parameterization, Zod, allowlists, review raw SQL |
| Malicious/exposed evidence | High | content/size check, malware scan, private storage, signed access, retention |
| Secret/PII leakage | High | secret manager, redaction, minimal input, safe errors, AI data minimization |
| Admin misuse | High | least privilege, reason, append-only audit, review/alert |
| AI prompt injection/harm | High | authorized retrieval, validated outputs, advisory boundary, human review |
| Chain key/false state | High | managed signer, least privilege, confirmations, reconciliation |
| DoS | Medium/High | rate/size limits, timeouts, bounded queues, monitoring |

Remaining controls include TLS ingress, secure tokens, ownership checks, signatures, idempotency, audit, upload controls, least-privilege DB, dependency review and backups. Environment errors must never echo raw values; do not serialize/log config objects with secrets (the env module marks secret properties non-enumerable). Keep .env and .env.* files ignored while explicitly allowing the placeholder-only .env.example. Choose bearer-header versus cookie token transport; cookies require CSRF defenses and secure SameSite policy. Rate-limit login, refresh, uploads, AI and expensive reads/writes; handle provider webhooks without breaking legitimate retries. The current express-rate-limit default store is in-memory and is suitable only for a single process; multi-instance production needs a shared store and consistent proxy/IP configuration. Test invalid tokens, escalation, cross-user access, mass assignment, invalid states, duplicate money operations, upload bypass and leaks. Establish incident, key rotation, vulnerability and reconciliation procedures before production.

TB-BE-022 uses restrictive deletion for transaction owners, participants, payment attempts, escrow, ledger accounts, journals and entries. TB-BE-023 keeps evidence files outside PostgreSQL and stores only an opaque private storage key plus sanitized metadata/hash. The key is not an access credential or URL; evidence access later requires authorization and private storage enforcement. Sanitize original filenames and validate content types/size in the upload task. Notification text must be minimal and contain no credentials or sensitive evidence content; notification records do not authorize access. Audit JSON metadata must be allowlisted/redacted and must never include passwords, tokens, payment credentials, raw evidence or unnecessary PII. TB-BE-026 stores only provider event identity plus optional allowlisted `eventData`; raw webhook bodies, signatures/authorization headers and payment credentials are forbidden. Idempotency uses a fixed-length HMAC request fingerprint, not raw request data; the HMAC secret remains in managed configuration and is never stored in the row. Use uniqueness to arbitrate duplicate webhook/idempotency submissions and atomic lease claims to prevent concurrent worker ownership; expired leases permit recovery but do not ensure exactly-once effects. Enforce status/attempt/lease invariants and append-only status history with reviewed SQL checks, grants/triggers and service controls before enabling producers/workers.

TB-BE-025's applied SQL includes CHECKs for canonical email (`lower(btrim(email))`), positive transaction/ledger amounts and evidence size, distinct buyer/seller, positive transaction/history versions, nonnegative escrow balance and nonnegative webhook/idempotency/outbox retry counters. PostgreSQL 17.10 catalog inspection and rolled-back negative/positive probes verified all 11. Email syntax, amount/currency bounds and participant-role matching remain service-level requirements. A CHECK cannot balance ledger rows across a journal; TB-BE-060 must use atomic serialized service posting, with a deferred constraint trigger (locking the journal owner) before enabling alternate writers. Ledger correction is via compensating journal only; append-only privileges/controls and broader runtime tests remain outstanding.

TB-BE-030 establishes auth-input policy and password primitives. Registration and login email inputs are trimmed, normalized to lowercase, validated as email addresses, and bounded to 320 characters. Registration passwords require at least 12 Unicode code points and allow at most 72 UTF-8 bytes, matching bcrypt's input limit; passwords are never trimmed and spaces/special characters are accepted (whitespace-only values are rejected). There are no arbitrary composition rules. Async bcrypt uses `BCRYPT_SALT_ROUNDS`, default 12 and bounded to 12–15 by validated environment configuration. Verification safely returns false for malformed hashes. Services do not log password values or hashes.

TB-BE-031 implements public `POST /api/v1/auth/register` and `/login`. Strict Zod schemas reject client-supplied role/status fields; registration assigns only `USER`/`ACTIVE`. The service hashes before DB work and creates User/Profile in one Prisma transaction; the database email unique constraint arbitrates concurrent attempts and `P2002` becomes a generic 409 conflict. Login verifies the hash and allows only `ACTIVE` users; unknown, wrong-password and inactive cases share one 401 code/message. Returned user projections exclude password hashes, roles and account status. Database failures return a safe generic 500. These routes do not issue JWTs or create sessions; login success here is credential verification only, not an authenticated session. Add abuse controls and timing/enumeration review before production.

TB-BE-032 issues HS256 access JWTs using validated secrets, issuer, audience and TTL; the payload contains only `sub` plus standard JWT claims. Verification pins algorithm/issuer/audience and normalizes token failures to generic 401. Opaque refresh tokens contain 256 bits from the system RNG; only SHA-256 digests are stored (raw tokens are returned once and never logged). Rotation conditionally revokes the predecessor and inserts a unique successor in one Prisma transaction; reuse of a rotated token marks reuse and revokes the family. A client retry after a winning concurrent rotation is treated as replay and can revoke the newly issued family. Logout idempotently revokes a known token and returns the same success for unknown tokens. Stateless access JWTs remain valid until expiry after logout/reuse, and user status is rechecked for each Bearer request. No access-token revocation list, dedicated auth rate policy, or live DB concurrency test is included; follow up in TB-BE-121 and production security review.

TB-BE-033 implements deny-by-default `requireRoles`, transaction participant, own-user, notification-owner, dispute-participant, evidence-participant, payment-attempt-participant and escrow-participant checks. Role policy is separate from participant policy: only persisted `USER`/`ADMIN` account roles are valid; participant authorization uses persisted `BUYER`/`SELLER` rows and verifies matching transaction buyer/seller identity. A creator relationship grants no participant access by itself. Dispute/evidence/payment/escrow checks follow their actual transaction relations; administrators do not implicitly bypass ownership checks. Missing/inactive identity returns 401, role denial returns 403, and absent or unauthorized resources share a generic 404 to reduce IDOR disclosure. No current business route is wired to these policies yet; each protected route must compose authentication then the applicable role/resource policy. Schema-level buyer/seller participant consistency is not enforced by a cross-table constraint, so inconsistent records fail closed.

## Privileged MFA persistence (TB-BE-034B)

MFA policy defaults: ADMIN accounts must use TOTP, USER accounts may opt in; TOTP has 6 digits, 30-second steps and a configurable `MFA_TOTP_WINDOW_STEPS` (0–2, default one step); each recovery-code set contains 10 single-use codes. This task implements persistence only: no login/step-up endpoint, required-ADMIN gate, or complete TOTP flow is active yet. TOTP secrets are AES-256-GCM authenticated ciphertext with a fresh 96-bit nonce, 128-bit tag, user/purpose-bound AAD, key identifier/version, and fail-closed decryption. A provider-neutral encryption-provider interface is implemented; providers perform encryption/decryption without exposing raw keys to application code, but production KMS is not configured. An optional 32-byte base64 local key is permitted only in development/test; it is omitted from `.env.example`, hidden from serialized configuration, and forbidden in production. Production MFA is therefore not production-ready until an approved KMS provider/key lifecycle is integrated.

Recovery-code plaintext is returned only at generation and only SHA-256 hashes are persisted. Conditional updates enforce one-time consumption and prior unused batches are invalidated transactionally. Challenges store only token hashes, expire, and cap attempts at five. Administrator recovery requires an independently verified opaque reference and two distinct active ADMIN approvals; target self-approval is denied. Approvals and security transitions write allowlisted audit events. Prisma service checks and unique constraints do not alone establish database immutability or all cross-row policy. PostgreSQL uniqueness/conditional writes protect duplicate use; actual concurrent behavior needs isolated PostgreSQL integration tests on a separately designated disposable database. Never log TOTP values, recovery codes, challenge tokens, ciphertext, hashes, provider keys or identity evidence.

## TOTP enrollment and verification (TB-BE-034C)

TOTP uses RFC 6238 HMAC-SHA1, a cryptographically random 160-bit secret, six-digit values and 30-second steps. Accepted codes can be within the validated 0–2 step skew window (default one); the server clock is authoritative. Enrollment remains pending until a valid code is verified, and active or unexpired pending enrollment cannot be silently replaced. Activation, replay-step claim and first recovery-code batch commit together; compare-and-set updates prevent accepting an already-used time step. Recovery code plaintext is returned only in the successful activation response or authorized regeneration response and cannot be fetched again. Authenticated verification permits five failed attempts per user per ten minutes by default; this limiter is in-memory and must use a shared store for multi-instance deployment. Logs omit request/response bodies and query strings; secrets, provisioning URIs and recovery codes are not logged. Production MFA remains blocked until a production KMS is selected/configured. TB-BE-034C itself did not add login MFA challenges; those are implemented in TB-BE-034D. Regeneration and TOTP-protected USER disablement are implemented under TB-BE-035-B.

## Login MFA and session assurance (TB-BE-034D)

Password login rate limit defaults to 10 attempts per IP per 15 minutes. Active-MFA USERs and all ADMINs must complete a short-lived (5-minute default, configured 60–900 seconds) LOGIN challenge; five wrong codes exhaust a challenge. The challenge token is 32 random bytes, returned once and stored only as SHA-256. Challenge verification binds account identity and purpose from the row; it rechecks active status/authVersion/current MFA, and atomically consumes the challenge with the TOTP replay-step claim. No session/refresh token exists while pending. Challenge verification also has a dedicated IP rate limit (5 per 10 minutes default). Both limits use process-local express-rate-limit stores; use a shared store before multi-instance deployment.

Access assurance is server-issued: JWT `mfa_at` means that this session completed TOTP at that server timestamp; `sid` binds it to the persisted refresh-session row and `av` to current User.authVersion. It does not assert recent verification forever, device trust, or recovery assurance. Middleware verifies current account role/status/version, persisted session MFA timestamp and revocation state. Password-only USER access JWTs remain valid to expiry after logout; MFA-assured tokens are denied once their linked session is revoked. Refresh rechecks role/status/version/MFA and preserves only persisted login assurance; it never upgrades a session. Security/role/password changes must increment authVersion and invalidate outstanding challenges/refresh sessions.

Existing ADMIN accounts without active MFA are denied normal login and therefore cannot use the authenticated enrollment endpoint. Promotion/provisioning must be gated on MFA setup. A reviewed bootstrap path for legacy ADMIN accounts is still required before broad ADMIN rollout; it must issue only a tightly scoped enrollment capability and is deferred to TB-BE-034G. No bypass session is provided by TB-BE-034D.

## Purpose-bound MFA step-up (TB-BE-034E)

Authenticated active-MFA sessions can request a five-minute default `STEP_UP` challenge only for an explicitly registered purpose. Current registration permits `MFA_RECOVERY_CODES_REGENERATE` on the caller's own User resource for USER/ADMIN and `MFA_DISABLE` on the caller's own User resource for USER. Their routes consume the matching one-time grant. Future purpose entries must declare resource type/cardinality, allowed account roles, maximum proof age, and whether ordinary role/ownership/consent authorization also applies. Never register broad purposes such as `ADMIN_ACTION` or treat possession of a grant as object authorization.

Step-up rows persist the challenge hash, account/authVersion, refresh-session FK, challenge category `STEP_UP`, distinct operation `operationPurpose`, resource type/ID, MFA enrollment activation timestamp, attempt count, expiry, consumption timestamp and server verification timestamp. The additive migration adds a restrictive session FK, lookup indexes and a named CHECK requiring complete session/operation/resource/enrollment binding for STEP_UP rows; login/recovery challenge rows must leave these fields null. Migration `20261103170000_step_up_assurance` was reviewed and applied to the approved local PostgreSQL 17.10 database; catalog checks confirmed all six columns, FK, indexes and validated CHECK. Verification checks current account, live non-expired session, current active enrollment and unchanged `enabledAt`. A serializable transaction conditionally advances the shared TOTP time step and consumes the challenge; any failed consume rolls back the TOTP claim. Five failed codes are durably capped per challenge. Logout or refresh rotation revokes the bound session and invalidates both outstanding challenges and grants. MFA disablement/re-enrollment changes the current activation timestamp and no longer matches prior grants; `authVersion` invalidates grants after authorization changes.

Successful step-up assurance is represented by the persisted consumed challenge, not a client-controlled claim or header and not an updated JWT `mfa_at`. The access/refresh session is unchanged. `createStepUpAuthorizationMiddleware` requires the registered purpose and resolves the resource from route context; it checks the same user/session/version/resource, current enabled MFA activation and server-time age. Compose it after authentication plus role and object ownership/participant middleware. A step-up proof does not establish ownership, settle payment, authorize custody, provide consent or decide a dispute. Recovery regeneration and USER MFA disablement consume one-time grants; no financial or dispute operation is authorized by this middleware.

Step-up creation/verification have separate default IP limits (five per ten minutes) and challenge attempts cap at five. Express stores are process-local; shared storage is a production prerequisite for horizontal deployment. The additive migration has been applied to the approved local PostgreSQL 17.10 database after read-only identity/migration preflight and SQL review. Real PostgreSQL concurrency coverage now runs on isolated `trustbridge_test`; it does not establish production multi-instance readiness. Production remains blocked on KMS, external identity-verification provider selection, controlled legacy ADMIN enrollment (TB-BE-034G), shared rate-limit storage and production security review.

## TB-BE-035-A1.2 — session assurance enforcement

Authentication assurance is signed as JWT claim `al` and cross-checked on every authenticated request against the persisted `RefreshToken.assuranceLevel`. Claims are rejected when missing, unknown, inconsistent with `mfa_at`, or different from session state. The request context takes assurance from the database session. `mfaVerifiedAt` remains TOTP-only evidence; recovery-code sessions have a null value and distinct `RECOVERY_CODE_VERIFIED` assurance. Recovery codes are consumed in the same serializable transaction that consumes the login MFA challenge. Refresh copies assurance unchanged and blocks sessions whose account, authorization version, active MFA or enrollment timing is no longer eligible. The legacy backfill remains authoritative; there is no runtime upgrade fallback.

`createRecentMfaMiddleware` and step-up challenge creation require `TOTP_VERIFIED`, so recovery authentication does not count as fresh TOTP or authorize a purpose-bound TOTP operation. Step-up grants retain their existing session/purpose/resource/version binding and one-time consumption behavior.

## TB-BE-035-A1.3 — PostgreSQL concurrency evidence

Six concurrency/integrity scenarios were executed against the separately created and migrated local `trustbridge_test` database using independent Prisma clients verified to use distinct PostgreSQL backend PIDs. Real PostgreSQL confirmed one-winner refresh rotation with family revocation; one-use recovery-code consumption; one-use step-up grant consumption with the challenge-verification `consumedAt` unchanged; denial of old grants and sessions after MFA enrollment replacement; access and refresh invalidation after authVersion changes; and transaction rollback for injected recovery-audit, grant-update and refresh-insert failures. The test DB contained no leftover records or trigger/function helpers after cleanup. This evidence is limited to those tested flows and does not establish production multi-instance readiness.

## TB-BE-035-B — recovery governance and MFA lifecycle

Recovery regeneration is protected by a server-registered one-time TOTP step-up purpose. The persistence transaction takes `FOR UPDATE` locks on the current `user_mfa` and refresh-session rows, verifies active account/enrollment, matching TOTP-assured session/authVersion and current enrollment timing, then invalidates every unused old code and inserts hashes for exactly ten new codes. A single transaction records an audit event containing only count/batch metadata; plaintext codes are returned once in the successful response. Because step-up consumption precedes the recovery-code transaction, an execution failure consumes the grant and requires a new TOTP step-up.

The existing login recovery path atomically consumes the hash-matched code and LOGIN challenge. It issues only `RECOVERY_CODE_VERIFIED`, leaves `mfaVerifiedAt` null, and cannot meet TOTP-only step-up checks. MFA disablement is available only to USER accounts after a one-time TOTP step-up; it locks enrollment/session rows, clears secrets and pending enrollment, invalidates unused codes, revokes refresh sessions and increments `authVersion`. MFA activation/re-enrollment uses the same enrollment-row lock. ADMIN self-disable is denied.

Recovery requests are serialized on their request row. Identity verification requires an injected independent verifier and records only an opaque reference/timestamp; absent a provider it fails closed. Approvals require two distinct active ADMIN accounts with active MFA, deny self-approval, reject duplicate decisions using the database uniqueness constraint, serialize approval updates with row locks, recheck eligible approvers and write privacy-safe audit events. Completion for an ordinary USER resets MFA, invalidates codes/sessions, increments `authVersion` and marks the request complete in one transaction. ADMIN recovery finalization is deliberately denied until controlled ADMIN re-enrollment is implemented; no public unauthenticated recovery request/identity endpoint exists. Prisma model declarations alone do not make approval/audit records immutable; production DB permissions/triggers remain a control to design.

Recovery/governance verification on 2026-11-03: isolated PostgreSQL 17.10 `trustbridge_test` (localhost:5432) with independent clients verified concurrent recovery-code login and regeneration, concurrent two-admin approvals, session invalidation, and rollback of recovery/login/finalization transactions. See DEVELOPMENT_LOG and TESTING_PLAN for exact counts. Production readiness remains blocked on a real identity-verification provider, ADMIN re-enrollment path, production KMS and shared rate-limit storage.

## TB-BE-035-C controlled legacy ADMIN enrollment

Legacy ADMINs without active MFA remain denied normal authentication and privileged access. The workflow reuses `AccountRecoveryRequest`, `RecoveryApproval`, `MfaChallenge`, `UserMfa`, and `AuditLog`. It requires an independent verification adapter, two distinct current MFA-enabled ADMIN approvals (excluding the subject), and a separate fresh TOTP one-time grant to issue authorization. The authorization token is random and short-lived; only SHA-256 hash is stored. Delivery occurs only through the injected out-of-band adapter, which is absent by default and fails closed.

Dedicated `LEGACY_ADMIN_MFA_ENROLL` and `LEGACY_ADMIN_MFA_VERIFY` challenge purposes bind operation and target by persisted purpose and `userId`; separate tokens make authorization consumption at enrollment start distinct from final TOTP proof. The migration adds enum values only; the existing step-up binding CHECK remains intact. Enrollment and finalization revalidate target role/status/authVersion, identity verification, request expiry, and two active MFA-enabled approvers under row locks. TOTP activation, challenge consumption, recovery-code issuance, pending challenge/grant expiration, session revocation, `authVersion` advance and audit writes commit atomically. Failure rolls back all state. Old access tokens fail authVersion checks; refresh tokens are revoked. No ADMIN can self-approve, and no static bypass exists.

Provider gates remain: no independently verified identity provider or secure delivery adapter is selected/configured. Thus the implementation and PostgreSQL tests establish the boundary, but production onboarding is blocked until provider configuration and operational verification. Existing step-up rate limiting remains process-local and is not multi-instance ready. Database-level audit immutability still needs separate permissions/triggers.

## TB-BE-035-D shared rate limiting

`src/services/rate-limit-store.service.js` provides a shared store contract. Production uses Redis `INCR` plus `PEXPIRE` in one Lua operation and disables the client's offline command queue; each request fails closed with a generic 503 if storage is unavailable. Local development and isolated unit tests may use an explicitly process-local memory store. Production environment validation rejects memory mode and requires a TLS `rediss://` URL with ACL username/password and a dedicated random `RATE_LIMIT_KEY_SECRET`. Secrets are non-enumerable in validated configuration and never included in errors, logs, health responses, or storage keys.

Rate-limit keys use HMAC-SHA256 over the operation, account identity, challenge token, or socket-derived IP. Valid email identities are trimmed/lowercased; authenticated user IDs come from verified server auth context. Opaque challenge values receive challenge-scoped buckets and are HMACed before storage; durable MFA challenge attempt caps remain in force. Forwarded-IP headers are not trusted (`trust proxy` is explicitly false); IPv6 addresses are grouped by /64. The global `/api/v1` IP bucket remains 100 requests/15 minutes. Existing login, MFA verification, and challenge windows/limits are retained, with account dimensions added where an identity is available. Registration and MFA enrollment initiation now also have bounded route limits. Password-reset endpoints do not exist yet; when introduced they must use the shared auth family and add account/IP/operation controls.

Liveness remains independent. `/health/ready` reports only whether the shared store is reachable (or `process_local` in development) alongside the existing honest `database: not_checked`; readiness stays 503 until database readiness is implemented. Graceful shutdown closes Redis. At the original D implementation stage no Redis service was available; D1 later verified multi-client shared counters against an isolated loopback Redis logical database `/15` (see below). Do not point the opt-in test at a shared or production Redis. Deployment still requires TLS, ACL-scoped credentials, network isolation, capacity/eviction monitoring, a consistent HMAC secret across instances, and a Redis availability/SLO plan. Production multi-instance deployment remains unverified until configuration and operational checks pass.

## TB-BE-035-E — production MFA encryption boundary

`src/services/mfa-crypto.service.js` now exposes a provider-neutral KMS envelope adapter. For each secret write it requests a fresh 256-bit DEK from an injected managed-KMS client, encrypts the MFA secret with AES-256-GCM and a fresh 96-bit nonce, and stores a versioned envelope containing the wrapped DEK in the existing ciphertext byte field. AAD binds ciphertext to user, purpose, key identifier and envelope version. The KEK stays in KMS; plaintext DEKs are held only during the operation and cleared from their buffers afterward. Decryption passes the stored key identifier/version and wrapped DEK to the KMS client, allowing a deployment adapter to resolve retained historical key versions. No schema migration or data re-encryption was required.

Production configuration requires `MFA_ENCRYPTION_PROVIDER=kms`, a non-secret KMS key identifier and positive envelope version, and rejects the local key. `createMfaService` also requires an injected `kms-envelope` provider whose key ID/version match validated config; local AES cannot be selected in production. Crypto/KMS errors are normalized to a generic failure, and `/health/ready` reports KMS availability for an injected production MFA service; enrollment/decryption operations fail closed on KMS errors. The adapter contract is implemented and mock-tested, but there is no cloud SDK/client, provider selection, workload identity, network policy or real test KMS configured. Consequently production MFA remains BLOCKED and NOT PRODUCTION-READY. Existing local-development ciphertext uses a different encoding and is not readable by this KMS envelope adapter; any data migration must be planned and verified separately before moving retained local-encrypted records to production. No such re-encryption was attempted.

Provider evaluation: no hosting platform or cloud SDK exists in the repository, so no vendor is selected. AWS KMS is a reasonable first candidate only if deployment is approved for AWS: its official documentation describes KMS envelope use and symmetric-key rotation. Otherwise the hosting platform's native KMS should be preferred to avoid cross-cloud identity/network dependencies. Manual provisioning must create a symmetric encryption key, grant the workload identity only data-key generation/decryption and key metadata access, separate key administration from application use, retain old key versions through rotation/rewrap, configure backup/recovery and deletion protection, monitor access/denials/latency, alert on availability failures, and test restore/rotation in a dedicated non-production account. Never put cloud credentials or KEKs in application config.
## TB-BE-036 user/account security

Self profile writes use a strict Zod allowlist and the authenticated user ID; roles, account status, email and security metadata are not writable from profile APIs. Password change requires current-password verification, plus one-time purpose-bound TOTP step-up for MFA-enabled accounts; the transaction locks the user row, rechecks the password, updates its hash, increments authVersion, revokes active refresh sessions and invalidates eligible old step-up grants. Self-deactivation requires current password and explicit confirmation; when MFA is enabled it additionally consumes a one-time TOTP step-up. ADMIN self-deactivation is denied through the self-service path. There is no permanent-delete operation.

ADMIN list/detail reads require persisted ADMIN authorization and recent TOTP.
