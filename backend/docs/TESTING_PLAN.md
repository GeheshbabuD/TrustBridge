# Testing Plan

Use Node.js built-in `node:test` (`npm test`); avoid a second test framework unless a later task demonstrates a specific need. Current suites cover the environment contract and the Express app/security middleware over ephemeral HTTP servers without a persistent listener or live database. HTTP coverage includes security headers, exact CORS allow/deny/preflight, API throttling and health exemption, request IDs, parser limits, safe 404/unexpected errors, completion-log fields and one-log behavior, secret/query/body exclusion, logger failure isolation, and liveness/readiness contracts. Readiness tests confirm no unavailable dependency is falsely marked healthy. Unit: validators, auth helpers, state matrix, money/currency, ledger invariants, risk rules, provider outputs. Integration: auth/user, transactions, Prisma constraints, payments/webhooks, escrow, disputes/evidence, notifications/admin. Security: token failures, escalation, cross-user access, webhook replay, duplicate release/refund, invalid state, mass assignment and upload abuse. Mock all external providers; never move real money. Smart-contract tests cover deployment, permissions, transitions and events. System tests cover OpenAPI/Postman, performance, resilience, migration upgrade and restore.

The approved disposable local migration/test target is PostgreSQL 17.10 at `localhost:5432/Trustbridge`; Prisma ORM 7.10.1 and its PostgreSQL adapter support this major version. The initial migration was generated create-only, reviewed, and applied after target re-verification. Future migrations still require SQL review and must never target an unknown or production database.

TB-BE-025 verified the approved local PostgreSQL 17.10 endpoint and empty baseline (allowing the existing empty `_prisma_migrations` table), applied `20261102153537_init`, and confirmed the migration is recorded once with no pending work. Post-application catalog checks found 15 enums, 21 application tables, 98 indexes (77 explicit plus 21 primary-key backing indexes), 33 restrictive foreign keys and 11 validated CHECK constraints. Each custom check rejected an invalid value and accepted a representative valid value in transactional probes; all probe writes were rolled back. These probes verify the actual PostgreSQL constraints but are not broader business/ledger-posting tests.

The TB-BE-025 final integrity review retains a static test for the named custom CHECK constraints in the migration. In addition, PostgreSQL 17.10 catalog verification confirmed all 11 are validated, and transactional probes exercised both rejection and valid-value acceptance; probe writes were rolled back. Ledger count/balance, posting concurrency, immutability and compensating-reversal behavior require TB-BE-060 service tests and broader TB-BE-121 PostgreSQL integration tests; a future deferred constraint trigger must be tested with concurrent writers and commits/reversals.
