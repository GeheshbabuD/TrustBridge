# Frontend Integration Readiness (TB-BE-045)

Source-level audit: 2026-11-12. Base path: `/api/v1`. Success responses use `{success,message,data}`; failures use a sanitized `{success:false,message,error:{code}}` envelope. Strict validation generally returns `400 VALIDATION_ERROR`; auth is 401, authorization 403, concealed unauthorized resources 404, unavailable dependencies 503. Exact service codes may vary. HTTP test references below are source evidence; this read-only audit did not run tests. Passing tests do not establish provider or production readiness.

## Contracts Member 1 can use now

Registration/login/MFA challenge/refresh/logout; authenticated profile/account; seller search; participant transaction/list/detail/terms/invitation/delivery; in-app notifications; participant dispute create/read/respond; and admin queues/review with the stated TOTP rules. Payment attempt APIs are staging-only until a checkout public-key/config contract and provider staging are available. Escrow release/refund responses mean authorization queued/recorded, not money moved. Evidence requires configured private storage. KYC and wallet have no frontend contract.

## Highest-priority blockers

1. Provide an approved Razorpay checkout key/config contract and verify it in staging while keeping live operations disabled.
2. Configure private evidence storage before enabling upload/download in a frontend environment.
3. Verify Route approval, seller linked-account resolution and release/refund/reconciliation in provider staging.
4. Configure email if the product promises email delivery; current notification APIs are in-app.
5. Keep KYC and wallet blocked pending product, provider and compliance approvals.

No tests or external services were run for this read-only audit. This report does not establish deployment readiness.
