# API Documentation Plan

Base `/api/v1`; registration, credential-verification login, MFA, recovery governance and the TB-BE-036 user/profile/account endpoints described below are implemented to their documented scope. Other listed endpoints remain planned. Generate OpenAPI and Postman after contracts stabilize.

Success envelope: { success: true, message: "Operation successful", data: {} }. Error: { success: false, message: "Operation failed", error: { code: "VALIDATION_ERROR" } }. Use safe messages, stable codes, correct HTTP status and pagination; never expose secrets, hashes or prompts.

Contracts are provisional; confirm frontend and policy needs. Never accept arbitrary status assignment. Enforce auth, role and ownership, validation, limits, redaction, idempotency and signatures.

Authorization middleware exports `requireAuthentication`, `requireRole`/`requireRoles`, `requireTransactionParticipant`, `requireOwnUser`, `requireOwnNotification`, `requireDisputeParticipant`, `requireEvidenceParticipant`, `requirePaymentAttemptParticipant`, and `requireEscrowParticipant`. Mount authentication first. Participant checks use only `request.auth.userId`, actual participant rows and transaction buyer/seller IDs. Resource checks return the same not-found response for missing and unauthorized IDs. No transaction, dispute, evidence or administrative endpoints are implemented or mounted by TB-BE-033.

Access JWTs contain standard issuer/audience/expiry claims, `av` (authorization version) and `sid` (refresh-session row ID); only sessions verified with MFA also contain server-signed `mfa_at` (Unix seconds). Bearer middleware checks current user status, role and authorization version. For MFA-assured requests it also checks the persisted session's user/version/MFA timestamp and revocation state. Refresh tokens are 32 random bytes encoded base64url and persisted only as a SHA-256 hash. Rotation is atomic; replay revokes its active family. Revocation is checked for MFA-assured access requests; password-only USER JWTs remain stateless and valid until expiry. PostgreSQL transaction concurrency still requires a designated disposable integration database.

## TOTP enrollment API (TB-BE-034C)

All three endpoints require an active authenticated Bearer account. Roles and status are loaded from the database. The enrollment endpoints do not change access-token assurance and do not protect login or privileged actions; those remain TB-BE-034D.

`POST /api/v1/auth/mfa/enroll` accepts `{}` and returns 201 with `data.enrollmentId`, `expiresAt`, `secret`, and `provisioningUri`. The Base32 secret and `otpauth://` URI are shown once to provision an authenticator; handle them as credentials. The pending secret is encrypted at rest. An existing active enrollment or unexpired pending enrollment returns a safe 409 and is never silently replaced. Expired pending enrollment may be restarted.

`POST /api/v1/auth/mfa/verify` accepts `{ "code": "123456" }`. A valid current or configured-skew-window code returns 200 with `{ "enabled": true, "recoveryCodes": [...] }`. This is the only response that displays this generated recovery-code batch; raw codes cannot be retrieved later. Incorrect/expired/replayed codes return a generic 400. Verification attempts are limited to five failures per authenticated user per ten minutes (configurable); the current rate-limit store is process-local.

`GET /api/v1/auth/mfa/status` returns only `{ enabled, enrollmentPending, requiredByPolicy, unusedRecoveryCodes }`. `requiredByPolicy` reflects the current persisted ADMIN role, but enrollment status alone does not grant assurance. Recovery-code login is implemented through the existing login challenge verification endpoint. Production enrollment remains unavailable until a production KMS provider is configured.

### Login challenge and recent assurance (TB-BE-034D)

`POST /api/v1/auth/login` verifies password first and reads role/MFA from PostgreSQL. Password-only USER without active MFA receives the normal session response. Active-MFA USER and ADMIN with enabled MFA receive `202 Accepted` with `data: { mfaRequired: true, challengeToken, expiresAt }`; no user details, access token or refresh token are returned in this stage. ADMIN without enabled MFA receives the generic `401 INVALID_CREDENTIALS` response.

`POST /api/v1/auth/mfa/challenge/verify` accepts only `{ "challengeToken": "<opaque>", "code": "123456" }`. It returns `200` and the standard access/refresh token response on success. The five-minute default challenge expires after five minutes, is purpose-bound to LOGIN and allows five failed codes. Invalid, expired, consumed, revoked-by-consumption, stale-authVersion, exhausted and wrong-purpose challenges share a generic `401 INVALID_MFA_CHALLENGE`. There is no account ID field. Password login is limited to 10 requests per IP per 15 minutes and challenge verification to 5 per IP per 10 minutes by default; both limits are configurable and process-local.

JWT `al` carries the signed session assurance level, while `mfa_at` is present only for TOTP-verified sessions. `sid` binds claims to the persisted refresh-token row and `av` is the account authorization version. It proves the recorded authentication method at issuance, not that TOTP remains recent forever or that the client device is trusted. Authenticated requests compare assurance and TOTP evidence to current session state. Refresh preserves stored assurance and never upgrades it. `requireRecentMfa` and purpose-specific step-up require TOTP assurance; recovery-code assurance does not satisfy those checks.

## Purpose-bound step-up (TB-BE-034E)

`POST /api/v1/auth/mfa/step-up/challenge` requires an active authenticated MFA session and accepts a strict body such as `{ "purpose": "MFA_RECOVERY_CODES_REGENERATE", "resourceId": "<current-user-uuid>" }`. It returns 201 with an opaque challenge token, expiry and safe purpose/resource metadata. The default lifetime is five minutes (`MFA_STEP_UP_CHALLENGE_TTL_SECONDS`, bounded to 60–600 seconds). Only the server registry in `src/services/step-up-purpose.registry.js` may permit a purpose. Recovery regeneration and MFA disablement are registered as one-time purposes on the authenticated user's own USER resource. Future modules must explicitly register operation-specific purposes with resource type/requirement, allowed roles, maximum age and additional-authorization policy.

`POST /api/v1/auth/mfa/step-up/verify` requires the same authenticated session and accepts only `{ "challengeToken": "<opaque>", "code": "123456" }`. The persisted challenge supplies user/session/purpose/resource, so client account, session, purpose and resource fields are rejected. Success returns purpose/resource and server verification time, without access/refresh tokens or a new session. Invalid, expired, consumed, mismatched, revoked, stale-version, inactive-MFA and exhausted challenges return a safe generic error. Both endpoints use dedicated configurable IP limits (five per ten minutes by default, in-memory/single-instance) plus a durable per-challenge five-attempt cap.

## Recovery-code management and MFA lifecycle (TB-BE-035-B)

`POST /api/v1/auth/mfa/recovery-codes/regenerate` requires an authenticated USER or ADMIN session, a matching one-time `MFA_RECOVERY_CODES_REGENERATE` step-up grant for that user's own USER resource, current active TOTP enrollment and a live TOTP-assured session. It returns `{ "codes": [ ...10 raw codes... ] }` once; hashes, batch identifiers and secrets are not returned. The grant is consumed before the downstream regeneration transaction, so a storage failure requires a new TOTP step-up. Regeneration locks the user's `user_mfa` and current refresh-session rows, then atomically invalidates unused old codes, stores hashes for exactly ten fresh codes and writes a redacted audit event. Status exposes only the unused-code count.

Recovery-code login remains `POST /api/v1/auth/mfa/challenge/verify` with the existing LOGIN challenge and a 32-character hexadecimal recovery code. The challenge and code are consumed in one transaction. The resulting session is `RECOVERY_CODE_VERIFIED`, has no `mfa_at`, cannot be replayed, and cannot satisfy TOTP-only recent-MFA or step-up authorization.

`POST /api/v1/auth/mfa/disable` requires an authenticated USER plus a one-time `MFA_DISABLE` TOTP step-up grant for that user's own resource. It clears active/pending secret material, invalidates unused recovery codes, revokes refresh sessions and increments `authVersion` atomically. ADMIN self-disable is denied. Account recovery request and identity-review endpoints are documented below for controlled legacy ADMIN enrollment; identity checks fail closed without a real independent verification provider. USER account-recovery finalization remains governed separately.

Future sensitive routes must compose authentication, role and resource ownership/participant checks, then `createStepUpAuthorizationMiddleware({ purpose, resourceId: request => request.params.<resource> })`. It checks a consumed recent challenge grant bound to the same user, live refresh session, auth version, purpose, resource and unchanged MFA enrollment. MFA proves only a recent second factor; it does not establish ownership, payment authorization, consent or authority to release funds or decide disputes. No sensitive business route currently uses this middleware.

Operational note: an existing ADMIN without active MFA receives only generic credential failure and cannot use authenticated enrollment because no normal session is issued. Do not promote or provision an ADMIN through the ordinary flow without completing MFA setup first. Controlled legacy ADMIN onboarding is implemented in TB-BE-035-C, but provider configuration remains a deployment gate; no bypass token is provided.

## Authentication assurance (TB-BE-035-A1.2)

Access JWTs contain `al`: `PASSWORD_ONLY`, `TOTP_VERIFIED`, or `RECOVERY_CODE_VERIFIED`. Authenticated requests require the signed value to match the live refresh-session row. `request.auth.assuranceLevel` is populated from persisted state, never request input. `mfa_at` and `RefreshToken.mfaVerifiedAt` remain exclusively TOTP evidence. The login challenge endpoint accepts either a six-digit TOTP code or a 32-character hexadecimal recovery code; recovery-code verification consumes the code once and creates a `RECOVERY_CODE_VERIFIED` session without TOTP evidence. Refresh preserves the existing level without elevation. Recovery-code sessions cannot pass recent-TOTP or purpose-bound step-up middleware.

## Controlled legacy ADMIN MFA onboarding (TB-BE-035-C)

An already-existing ADMIN without active MFA cannot obtain a normal session or use privileged routes. An authenticated active ADMIN can view the restricted inventory via `GET /api/v1/auth/mfa/admin-enrollment/legacy-admins`; the response contains only each account's ID and email. A different active, MFA-enabled ADMIN may create a short-lived review request for that account through `POST /api/v1/auth/mfa/admin-enrollment/requests` with `{ "targetUserId": "<uuid>" }`. The request is not an approval and does not grant access. Independent identity verification is invoked through `POST /api/v1/auth/mfa/admin-enrollment/requests/:requestId/identity` with an opaque provider reference; the configured verifier must independently validate it. The application returns only a verified flag and never accepts a client assertion as verification.

Two distinct active, MFA-enabled ADMINs must each submit `POST /api/v1/auth/mfa/admin-enrollment/requests/:requestId/approval` with an explicit decision and safe reason code. Each approval requires a fresh, one-time `ADMIN_RECOVERY_APPROVAL` TOTP step-up. The target cannot approve their own request; duplicate or competing decisions are serialized and denied. After approval, a qualified ADMIN with fresh, one-time `LEGACY_ADMIN_MFA_ENROLL_AUTHORIZE` step-up calls `POST /api/v1/auth/mfa/admin-enrollment/requests/:requestId/authorize`. The server creates a ten-minute random authorization, stores only its hash, and sends it only through the configured out-of-band delivery adapter. The response contains expiry/status, never the token. If identity or delivery adapters are unavailable, the workflow fails closed.

The target ADMIN submits `POST /api/v1/auth/mfa/legacy-admin-enrollment/start` with `{ "authorizationToken": "<one-time token>" }`. A successful call consumes that authorization and returns the one-time TOTP provisioning material plus a separate opaque verification token. `POST /api/v1/auth/mfa/legacy-admin-enrollment/verify` accepts `{ "verificationToken": "<opaque token>", "code": "123456" }`. Successful TOTP verification enables MFA, returns ten recovery codes once, expires other pending challenges/grants, revokes all existing refresh sessions, and increments `authVersion`. It does not issue a session; the ADMIN must sign in with password and TOTP. The verification token is hash-only, purpose-specific, single-use and expires with the enrollment authorization. Invalid responses are generic and rate limited. The two dedicated purpose enum values were added additively; no schema models were duplicated.

The identity verifier and secure delivery adapter are injectable boundaries. Neither is configured in the current deployment, so real onboarding remains unavailable until those providers are selected, configured and verified.

## User and profile management (TB-BE-036)

`GET /api/v1/users/me` returns the authenticated user's safe account summary and profile. `PATCH /api/v1/users/me` accepts only a strict allowlist: `displayName` (trimmed, nullable), `preferences` (`locale`, `timeZone`) and `notificationPreferences` (`transactionUpdates`, `productUpdates`). Locale and time zone are normalized. Email, role, status, authVersion, MFA state, credentials and tokens are never writable through this route.

`POST /api/v1/users/me/password` accepts `{ "currentPassword": "...", "newPassword": "..." }`. It rechecks the current password while holding the user row lock, requires one-time TOTP step-up for MFA-enabled accounts, changes the bcrypt hash, increments authVersion, revokes all active refresh sessions and invalidates persisted step-up grants in one transaction. The response confirms session invalidation; the user must authenticate again.

`POST /api/v1/users/me/deactivate` accepts `{ "currentPassword": "...", "confirmation": "DEACTIVATE" }`. The current password is verified before the optional step-up; MFA-enabled USER accounts must also complete one-time `USER_ACCOUNT_DEACTIVATE` TOTP step-up. ADMIN self-deactivation is not available here and requires a governed process. Deactivation is soft status change only: historical and financial records are retained, authVersion advances and sessions are revoked.

ADMIN user endpoints are `GET /api/v1/admin/users?limit=25&cursor=<uuid>&status=ACTIVE`, `GET /api/v1/admin/users/:userId`, and `PATCH /api/v1/admin/users/:userId/status` with `{ "status": "SUSPENDED", "reasonCode": "SECURITY_REVIEW" }`. Reads require ADMIN plus recent TOTP. Status changes require ADMIN plus one-time `ADMIN_USER_STATUS_UPDATE` step-up bound to the target user; the acting admin/session/MFA are rechecked transactionally. An administrator cannot target their own account, the last active MFA-enabled ADMIN cannot be suspended/deactivated, deactivated accounts cannot be reactivated, and every changed status is audited with allowlisted metadata. This API does not assign roles; there is no self-promotion or role-mutation endpoint.

All routes return safe JSON, never hashes/secrets/tokens. Missing/unauthorized access uses existing authentication/RBAC errors; invalid strict bodies return `400 VALIDATION_ERROR`. Profile updates are owner-scoped by `request.auth.userId`.

TB-BE-036 review verification: focused HTTP tests confirm authentication, strict field allowlists, reauthentication and ADMIN RBAC; real PostgreSQL service integration on the isolated `trustbridge_test` database confirms persisted profile preference updates, session/authVersion invalidation, audited status changes and rollback. The additive Profile migration is not applied to the development database; that environment must not run these routes until its migration sequence is separately reviewed and authorized.

## Transaction lifecycle (TB-BE-037)

- `POST /api/v1/transactions` requires an authenticated USER, `Idempotency-Key`, seller UUID, positive `amountMinor` as a decimal string, supported uppercase ISO currency code, and bounded JSON terms. Buyer identity is always the authenticated user. Seller must be a distinct active USER. Creates the transaction, buyer/seller participant rows, initial `CREATED` history and audit record atomically. Replaying the same key/input returns the original safe transaction; a different input with the same key returns `409 IDEMPOTENCY_KEY_REUSED`.
- `GET /api/v1/transactions` lists only persisted participant transactions; optional filters: `cursor`, `limit` (1–100), `status`.
- `GET /api/v1/transactions/:transactionId` and `/history` require a persisted BUYER or SELLER participant whose role agrees with the transaction's buyer/seller foreign key. Missing and nonparticipant resources share 404.
- `POST /api/v1/transactions/:transactionId/transitions` accepts `{ "status": "ACCEPTED", "expectedVersion": 1 }`. The server derives actor/role; it never accepts buyer, seller, actor, creator, amount, terms, or arbitrary status mutation from a transition request. Role and transition rules are listed in the Architecture/Database design docs. Success appends status history and a safe audit event atomically; stale versions return 409.

Responses serialize minor-unit amounts as decimal strings and omit payment attempts, escrow, ledger, credentials, MFA/session data and internal relations. In TB-BE-037 the supported transitions stop at `AWAITING_PAYMENT`/`CANCELLED`/`REJECTED`; a client cannot mark a transaction funded, disputed, paid out, refunded or completed. Those transitions require their later verified payment/dispute/payout/refund workflows.

## Payment foundation (TB-BE-038 Phase 2)

- `POST /api/v1/transactions/:transactionId/payment-attempts` requires an authenticated USER who is the persisted BUYER participant and an `Idempotency-Key`. Send an empty JSON object (or an empty body). Amount, currency, provider reference and status are taken from the current persisted accepted terms; client-supplied fields are rejected with `400 VALIDATION_ERROR`. Success is `202` with the safe attempt ID/status, amountMinor string, currency and timestamps. When an enabled Razorpay adapter has persisted its order, the response also includes `checkout: { key, order_id, amount, currency }`; `key` is the public Razorpay key ID, `order_id` and INR amount come from the persisted attempt, and neither API nor webhook secret is returned. This does not mean the provider captured funds.
- Repeated identical idempotency keys return the same attempt. Conflicting key reuse or an existing active attempt returns `409`. A missing/unconfigured adapter or provider outage fails closed; an ambiguous provider call remains pending.
- `GET /api/v1/payment-attempts/:paymentAttemptId` is restricted to persisted transaction participants and returns only safe attempt summary fields. If the persisted attempt is still pending and its Razorpay order is available, it may also include the same safe `checkout` object; otherwise status retrieval remains available without checkout configuration.
- `POST /api/v1/webhooks/:provider` is provider-authenticated through the configured adapter's signature verifier. The server verifies the original request bytes before processing. Invalid signatures and malformed normalized events do not mutate payment state or create trusted inbox records. The provider/account/event ID has a database unique constraint. The inbox stores a SHA-256 digest of the signature-verified raw body in its allowlisted `eventData`; identical duplicates are idempotently acknowledged. Reuse of an event ID with different content preserves the originally accepted event data, marks an integrity error and appends a privacy-safe audit alert; the endpoint returns sanitized `202` review acknowledgment, not an ordinary duplicate response. Conflicting content never updates payment or escrow state. The Razorpay adapter is implemented, but payment enablement and provider eligibility remain deployment-gated. Operation-specific shared rate-limit buckets supplement the global API limit; production fails closed when shared storage is unavailable.

## Razorpay adapter (TB-BE-070)

- When configured with `PAYMENT_PROVIDER=razorpay` and payments explicitly enabled, `POST /api/v1/transactions/:transactionId/payment-attempts` creates a server-side Razorpay Order. Persisted minor units are sent as integer paise and currency must be `INR`; a persisted attempt UUID is the order receipt. Ambiguous creation retries query Razorpay by that receipt before creating again.
- `POST /api/v1/payment-attempts/:paymentAttemptId/verify` accepts strict `{ "orderId", "paymentId", "signature" }`; server verifies the checkout HMAC, fetches the payment through Razorpay API, checks order/amount/currency and records only a verified captured outcome. It cannot accept a client status claim.
- Razorpay webhook route uses `X-Razorpay-Signature` on exact raw body and requires `x-razorpay-event-id`. `payment.failed` stays pending until authoritative reconciliation resolves the order; duplicate/out-of-order events use the existing webhook inbox rules.
- No refund or Route HTTP operation is exposed. Adapter refund/Route methods are disabled unless separately enabled and authorized by an injected financial policy. TB-BE-039 authorization, Razorpay account approval, Route eligibility and legal custody review are still required. Provider capture is not settlement or transaction completion.

Payment capture, escrow funding, seller release and refund are represented by separate persisted lifecycle records and authorization/execution services; capture does not release/refund money or complete a transaction. **Current implementation limitation:** verified capture processing currently invokes the escrow funding service in the same database transaction and transitions the transaction to `FUNDED` (see TB-BE-048 progress note). This is an internal escrow accounting posting, not verified provider settlement or legal custody. A distinct authoritative settlement-evidence event/gate is not implemented, so production settlement assumptions remain unresolved and must not be inferred from this API response.
# TB-BE-050 transaction transition policy (2026-11-04)

## Delivery workflow (TB-BE-050)

- `POST /api/v1/transactions/:transactionId/work/start` — seller participant only; body `{ "expectedVersion": 5 }`; requires persisted FUNDED escrow and advances FUNDED to IN_PROGRESS.
- `POST /api/v1/transactions/:transactionId/deliveries` — seller only; body `{ "expectedVersion": 6, "description": "..." }`; creates a numbered delivery record and advances IN_PROGRESS to DELIVERED atomically.
- `GET /api/v1/transactions/:transactionId/deliveries` — active buyer/seller participant only; returns safe submission, decision and evidence metadata.
- `POST /api/v1/transactions/:transactionId/deliveries/decision` — buyer only; body `{ "deliveryId": "uuid", "expectedVersion": 7, "decision": "ACCEPTED" | "CHANGES_REQUESTED", "reason": "optional" }`. `ACCEPTED` requires the number of evidence records specified in the accepted terms. `CHANGES_REQUESTED` returns the transaction to IN_PROGRESS and requires a new seller submission.
- `POST /api/v1/transactions/:transactionId/deliveries/:deliveryId/evidence` — seller participant only, raw PDF/PNG/JPEG/WebP body, max 10 MiB; headers `X-Evidence-Category` (DELIVERY, WORK_PROGRESS, COMMUNICATION, OTHER) and optional `X-Evidence-Filename`. Evidence storage must be configured; the response contains metadata only.
- `GET /api/v1/transaction-delivery-evidence/:evidenceId` — buyer/seller participants only; private no-store download, integrity-checked and audited.

These endpoints do not prove payment, escrow custody, transaction completion, or payout. Buyer acceptance is not a release instruction. Release still uses the existing fresh-TOTP `ESCROW_RELEASE` authorization path. ADMIN has no participant bypass. Errors include validation 400, ownership-safe 404, state/version conflict 409, and storage-unavailable 503.

Existing routes remain `POST /api/v1/transactions`, participant-scoped reads/history, and `POST /api/v1/transactions/:transactionId/transitions` with strict `{ "status": "...", "expectedVersion": n }`. The service—not client claims—authorizes a transition from persisted buyer/seller membership and current account/authVersion under transaction row lock. Supported participant edges remain seller `CREATED→ACCEPTED/REJECTED`; buyer `CREATED→CANCELLED`; buyer `ACCEPTED→AWAITING_PAYMENT`; and buyer `AWAITING_PAYMENT→CANCELLED` only when no payment attempt exists.

If any payment attempt exists during awaiting-payment cancellation, return HTTP 409 with `error.code=PAYMENT_OUTCOME_UNVERIFIED`. It applies to all persisted attempt statuses until a verified provider-outcome service exists. Storage failure returns sanitized HTTP 503. Stale versions and other unsupported/invalid transitions return HTTP 409; validation remains HTTP 400, nonparticipant resources remain concealed as 404, and ADMIN has no ownership bypass. No endpoint can mark a payment funded, decide a dispute, release/refund money, or mark a payout/refund complete. Retries at a stale version do not create another history/audit entry; create endpoint idempotency behavior is unchanged.

## Transaction terms and seller invitation (TB-BE-051)

- `GET /api/v1/transactions/:transactionId/terms` returns versioned terms and participant decisions to a verified buyer or seller only.
- `POST /api/v1/transactions/:transactionId/terms/versions` accepts positive integer minor units, uppercase supported ISO currency, and a strict structured terms object (description, optional scope/delivery dates or days, milestones, evidence/acceptance requirements and policy references). A new version is proposed; the prior pending version is superseded. Terms may change only before a payment attempt, escrow or dispute exists.
- `POST /api/v1/transactions/:transactionId/terms/decisions` accepts `{ "version": 1, "decision": "ACCEPTED" }` or `REJECTED`. Each participant can decide once per version. The agreed snapshot updates only after both persisted buyer and seller accept. Rejection closes that version; a later proposal is a new version. Terms consent does not initiate payment, fund escrow or authorize release.
- `POST /api/v1/transactions/:transactionId/invitations` is buyer-participant-only and may invite only the transaction's active USER seller. It returns the opaque 256-bit invitation token only in this dedicated issuance response; only its SHA-256 hash is stored. The token expires after seven days. No token appears in transaction reads, ordinary responses, audit metadata or logs. Until a delivery provider exists, the caller must securely transmit this one-time issuance value.
- `POST /api/v1/transaction-invitations/accept` and `/reject` accept `{ "token": "...", "expectedVersion": 1 }`. The authenticated identity must match the eligible active USER invitee; tokens are single-use. Invalid, expired, revoked, replayed and wrong-user tokens return the same 404. Acceptance records invitation consent but does not accept the transaction. Rejection atomically records seller rejection and moves `CREATED` to `REJECTED` with history/audit.
- Seller `CREATED→ACCEPTED` requires both participant approvals of the current terms and an accepted seller invitation. Pending invitations are revoked when a transition makes the transaction ineligible. These endpoints never mark payment/escrow outcomes or execute financial actions.

Payment initiation and webhook routes also use operation-specific shared rate-limit buckets in addition to the global `/api/v1` limiter. Initiation keys use the authenticated user and socket IP dimensions; webhook requests use the operation/IP dimension. Production requests fail closed if the shared rate-limit store is unavailable.

## TB-BE-039 — Escrow endpoints (authorization foundation; provider execution pending)

- `GET /api/v1/transactions/:transactionId/escrow` requires authentication and persisted transaction participation. Returns only escrow ID, transaction ID, status, decimal-string `balanceMinor`, and currency.
- `POST /api/v1/transactions/:transactionId/escrow/release` requires buyer participant ownership, strict `BUYER_ACCEPTED_DELIVERY` reason, `Idempotency-Key`, and a single-use recent TOTP step-up grant for `ESCROW_RELEASE` bound to this transaction and session. Returns 202 with the operation ID and `PENDING`; idempotent replay returns the same operation.
- `POST /api/v1/transactions/:transactionId/escrow/refund` requires persisted ADMIN role, strict `ADMIN_RESOLVED_REFUND` reason, `Idempotency-Key`, `ESCROW_REFUND` TOTP step-up, and the service's resolved-refund/dispute and funded-escrow checks. This does not resolve a dispute or execute a refund. Returns 202 with a pending operation.

Neither endpoint moves money. No provider execution route is exposed. Final `COMPLETED`/`REFUNDED` occurs only through an internal executor result verified for provider identity/reference, exact amount and currency, after which a balanced journal and final status/history/audit commit atomically. Ambiguous outcomes stay pending.

## TB-BE-090 — Transaction risk assessment API

`POST /api/v1/admin/transactions/:transactionId/risk-assessments` requires an authenticated ADMIN, recent TOTP assurance (maximum five minutes), the operation-specific shared rate limit and an empty JSON body. It accepts no client amount, status, participant identifiers or evidence. Success returns 201 and an advisory assessment (`score`, `riskLevel`, indicators/explanations, ordinal `confidence.level` with `calibrated: false`, recommendation, provenance and `PENDING` human-review status). Disabled provider or upstream timeout, throttling, malformed response or persistence outage returns generic 503; a transaction changed during inference returns 409. AI scores/recommendations never authorize or execute financial or account actions.

`POST /api/v1/admin/transactions/:transactionId/risk-baselines` creates a provider-independent deterministic assessment. It requires authentication, ADMIN role, recent TOTP (maximum five minutes), an operation-specific shared rate limit and an empty body. Success returns 201 with `RiskAssessment` status, nullable score, category (`LOW`, `MEDIUM`, `HIGH`, or `INSUFFICIENT_DATA`), reason-coded findings, input field paths, `trustbridge-risk-baseline.v1`, `transaction-risk.v1`, source transaction version and assessment time. No participant identities, descriptions or evidence are returned. Each request appends history. Invalid/incomplete input returns an explicit `INSUFFICIENT_DATA` record; stale source data returns 409 and storage failure returns generic 503. Categories are advisory review priority only and cannot authorize financial, account or dispute action.

`POST /api/v1/admin/disputes/:disputeId/assistance` requires authenticated ADMIN access, a one-time recent-TOTP `DISPUTE_REVIEW` step-up grant bound to the dispute, a dedicated shared rate limit, and an empty body. It is available only while the persisted dispute is `UNDER_REVIEW`. Success returns 201 with a structured advisory summary, suggested category, missing-evidence categories, review steps and model provenance; it is persisted as pending `AIAnalysis` history. Client-supplied narrative, resolution or evidence is rejected. The provider input excludes evidence contents, filenames, storage keys and user/transaction identifiers. Stale dispute version returns 409; disabled/unavailable provider or persistence error returns generic 503; invalid minimized input returns 422. This endpoint cannot resolve or modify a dispute or initiate any financial action.

### Notifications and email (TB-BE-041)

`GET /api/v1/notifications?limit=25&cursor=<notification-id>` returns a paginated list belonging only to the authenticated user. `POST /api/v1/notifications/:notificationId/read` marks that user's notification read and is idempotent; another user's or missing ID returns the same 404. Responses contain allowlisted notification fields only. Transaction, payment, escrow, delivery and dispute events enqueue durable `USER_NOTIFICATION` outbox records inside their originating transaction. Workers honor stored notification preferences and deduplicate by recipient/event. Email uses an injected provider adapter and stable idempotency key; delivery is disabled by default until configured. No endpoint exposes provider payloads, outbox internals or private resource content.

### Blockchain (TB-BE-043)

No public blockchain API is exposed. Approved internal transaction status-history writes may enqueue a hash-only outbox commitment. Chain submission and receipt reconciliation run in a supervised worker; blockchain records are operational metadata only and never alter HTTP authorization, payment, escrow, ledger or dispute decisions.

### Wallet balance/history API (pending accounting design)

Wallet balance and transaction-history endpoints are not implemented. Before implementation, define ownership, posted/pending/reversal semantics, per-currency balances and explicit escrow exclusion. Then add read-only API contracts and tests against the approved wallet ledger source.

## Seller and administrator listing APIs (Phase 3)

`GET /api/v1/sellers?q=<display-name>&limit=25&cursor=<uuid>` requires authentication. Search is case-insensitive over active USER profiles with a non-empty `displayName`. The response contains only `id` and `displayName`; email, account status, preferences, authentication/MFA fields and payment data are excluded. Results sort by display name then user ID. `q` must be 2–80 characters, `limit` is 1–100, and unknown query parameters are rejected.

`GET /api/v1/admin/transactions?status=CREATED&buyerId=<uuid>&sellerId=<uuid>&createdFrom=<ISO-8601>&createdTo=<ISO-8601>&limit=25&cursor=<uuid>` requires authenticated ADMIN and a TOTP assurance timestamp no older than five minutes. Production uses a dedicated shared rate limit; if the shared store is unavailable, the route fails closed. Results sort by `createdAt DESC, id DESC`; fields are transaction ID, buyer/seller IDs, status, integer-minor amount as a decimal string, currency, version and timestamps. Terms, payment attempts, provider references and private data are omitted.

`GET /api/v1/admin/disputes?status=OPEN&limit=25&cursor=<uuid>` has the same ADMIN, recent-TOTP and production shared-rate-limit requirements. Results sort by `createdAt DESC, id DESC` and contain only dispute/transaction/submitter IDs, status, category, timestamps, deadlines and version. Description, resolution text and evidence contents/references are omitted.

All three use the standard success/error envelopes. Invalid/unknown query fields return sanitized 400 `VALIDATION_ERROR`; unauthenticated requests return 401; non-admin or stale/missing TOTP returns 403; storage/shared rate-limit failures fail safely. Admin listing authorization is not a transaction ownership bypass. Example success data: `{ "sellers": [{ "id": "…", "displayName": "Ada" }], "nextCursor": null }`; admin responses use `transactions` or `disputes` with the documented safe projections and `nextCursor`.

## TB-BE-046 API addition

`POST /api/v1/auth/logout-all` requires a valid Bearer access token and accepts no account identifier. It revokes all active refresh sessions belonging to `request.auth.userId` and returns `{success:true,data:{loggedOut:true,revokedCount:number}}`. Existing `POST /auth/logout` continues to revoke a specific presented refresh token; refresh-token reuse continues to revoke the full family. Authenticated requests backed by revoked sessions fail persisted-session validation.
