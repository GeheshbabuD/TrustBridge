# Blockchain Architecture

Blockchain is an optional tamper-evidence layer, not proof of custody. Select a network only after cost, privacy, finality, reliability and legal review. Hash canonical important events and store minimum commitments/references. Keep personal data, credentials, payment data and evidence off-chain; assess hash leakage.

A local Solidity prototype may record role-authorized state references and emit events, but must not custody real funds. Use durable outbox, idempotency, retries, confirmation/reorg policy and reconciliation. Compare event hashes and chain references; inconsistent or failed writes stay pending/failed, never reported as completed escrow. Keep signing keys outside source/logs in managed custody, scope signer privileges, define rotation/recovery and contract/network allowlist. Test locally first. Testnet needs approval/credentials. Mainnet/funds require independent audit, key management, incident response and legal review.

TB-BE-024 adds the persistence-only `BlockchainRecord`: transaction-scoped idempotency, network/contract reference, operation type, event hash, optional transaction/block references, status and safe error code. Multiple records per transaction are valid. It contains no raw payload or signing secrets. `SUBMITTED` and even a stored transaction hash do not establish confirmation or finality; later verification/reorg monitoring and reconciliation must govern confirmed status. No chain SDK or execution was added.

## TB-BE-043 local prototype status (2026-11-07)

The non-custodial `TrustBridgeEventAnchor.sol` prototype accepts domain-separated SHA-256 commitments for transaction status-history versions. It stores no raw transaction data, identity, payment metadata or evidence. A transaction's event hash and minimal `BlockchainRecord`/`BLOCKCHAIN_ANCHOR` outbox row are inserted in the same PostgreSQL transaction as status history. Existing transaction status, payment, escrow, dispute and ledger records remain authoritative; chain data never grants authority or changes business state.

The Ethers v6 adapter verifies the configured chain ID, deployed contract code and active writer allowlist. It reports broadcast as `SUBMITTED`; it marks `CONFIRMED` only after a matching contract event and stored hash are found in a canonical successful receipt at the configured confirmation depth. Missing receipts, timeouts and shallow confirmations remain pending. Reconciliation detects receipt/hash changes and requeues the same idempotency key after a possible reorg. Outbox leases serialize worker claims. An adapter requires an injected signer; no private-key environment variable, production KMS or signing provider was added.

Integration is disabled by default. RPC URL, contract address, chain ID and a network-approved confirmation depth are required to enable configuration; production RPC must use TLS. The app refuses to start blockchain execution without an explicitly injected signing adapter. ADR-007 still selects no network; testnet, signer custody, contract review and deployment are not verified. Local tests use ephemeral Ganache and test-only deterministic accounts; no testnet or production operation occurred. Hashes can still leak correlation/equality and must not include secrets or low-entropy/private fields.
